# v0.4 Hosted: auth design input

**Date:** 2026-11-02
**Status:** Brainstorm, not yet planned. Input for `/paul:discuss-milestone` for v0.4.

## Goal

Run inio-mcp as a hosted service on EKS. First for the owner and team (internal, one tenant), later for Inio clients (many tenants). Clients in scope: Claude Desktop / claude.ai, Claude Code, VS Code, Cursor. ChatGPT is deferred until the hosted server has OAuth.

## Current Keycloak landscape (v26.5.4, can upgrade)

| Realm | Purpose | Notes |
|-------|---------|-------|
| api2api | Machine clients (client_credentials) | Holds each tenant's client id/secret; token carries `inio_client_id`; APISIX introspects against it |
| BoP | Back-office portal users (OIDC + PKCE) | RBAC; some power users (internal and client-side) see all clients' data; BoP calls APISIX via its own presentation backend |
| 3rd party | Webhook senders (e.g. SendGrid) | Not relevant here |

## Decision direction: dedicated MCP realm

- New realm `mcp`. Starts with zero access; tenant and write rights are granted explicitly by an admin.
- **No extra credentials:** BoP (and/or internal SSO) added as an identity provider; users log in with their existing account. First broker login creates a local user. BoP roles are **not** mapped automatically, so BoP power-user reach does not leak into the MCP.
- **Per-user write rights:** realm role (e.g. `mcp-writer`) in the token; the MCP server hides/rejects write tools without it. Replaces the global `INIO_ALLOW_WRITES` for the hosted server and covers most of AEGIS R3.
- **Tenant assignment:** user attribute in the MCP realm, emitted as a claim. One tenant per user at first; multi-tenant power users (tenant list + `tenant` tool argument) deferred until needed.
- **Audit:** Keycloak events cover logins and token issuance only. Tool-level audit (user `sub`/`preferred_username`, tool, target, outcome) comes from MCP server logs (AEGIS R8 with real identity).

Rejected:
- Reusing BoP tokens directly: carries power-user cross-tenant reach into the MCP.
- Cross-realm "external to internal" token exchange (legacy V1, preview).
- Users in the api2api realm: breaks the machine-only segregation.

## Open question: API token for the user's tenant

| Option | How | Trade-off |
|--------|-----|-----------|
| **1. Dedicated per-tenant api2api client for the MCP** (start here) | `inio-mcp-<tenant>` client per tenant in api2api; secrets in AWS Secrets Manager; server selects by the user's tenant claim | No gateway change; per-tenant revocation separate from the tenant's own integration. Server holds a secret per onboarded tenant; API sees the client, not the person |
| **2. APISIX trusts the MCP realm** (later) | Intra-realm token exchange (standard v2, supported in 26.5) to `aud=inio-api` with `inio_client_id` from the user attribute; APISIX accepts the MCP realm issuer on public API routes | No stored secrets; API sees the real user. Gateway work; the admin-set tenant claim must be protected like the api2api realm |

## MCP server work implied

- OAuth resource server: validate the MCP realm JWT (issuer, audience, expiry) on `/mcp`; publish Protected Resource Metadata (`/.well-known/oauth-protected-resource`) pointing at the realm.
- Per-request identity: request context carries user, tenant and roles (AEGIS R9 seam).
- Per-tenant Inio client/token cache (option 1) instead of the single process-wide client.
- Role-based write tool gating; per-user tool logging.
- Fixed `MCP_AUTH_TOKEN` mode stays for self-hosted single-tenant installs.

## To verify in research

- How Claude clients register as OAuth clients: pre-registered client, Client ID Metadata Documents (support in Keycloak 26.5?), or Dynamic Client Registration restricted by policy (lower risk in a dedicated realm).
- Audience / resource indicator handling in Keycloak (audience mapper vs RFC 8707 `resource`).
- Claude Desktop / claude.ai custom connector OAuth requirements (redirect URIs, scopes).

## Staging

1. **Internal, fixed token:** EKS deployment (Helm chart), one tenant, `MCP_AUTH_TOKEN`. No Keycloak work. Claude Code / VS Code / Cursor send the header; Claude Desktop keeps local npx.
2. **Internal + OAuth:** MCP realm with BoP brokering; token validation, PRM, role-gated writes, per-user logs; tenant credentials via option 1.
3. **Multi-tenant:** onboard client tenants; move to option 2 when per-tenant secrets become a burden.
