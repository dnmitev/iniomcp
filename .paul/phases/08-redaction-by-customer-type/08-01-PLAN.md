<objective>
## Goal
Make redaction depend on the customer type. Business customers (`customerType` `B`) are returned in full except the bearer invoice links. Consumers (`C`), and any data whose type is unknown, keep today's redaction plus customer name, city, `yourReference` and `note`. `get_invoice` finds the type by looking up the invoice's customer (cached), falling back to consumer rules. A key-drift check fails when the API returns keys nobody has reviewed.

## Purpose
The LLM is meant to be an easy integration layer. Business contact data is public (company registers, maps) and hiding it makes the assistant less useful, while consumer data stays protected for GDPR. This is the reworked AEGIS R2 (F-05-001, F-01-004, F-05-005).

## Output
- `src/redact.ts`: type-aware `redact`, updated `REDACTION_NOTE`
- `src/tools/result.ts`: `present`/`presentRaw`/`presentPage` pass the type through
- `src/tools/get-invoice.ts` + `src/server.ts`: customer-type lookup with a shared cache
- README Data protection section rewritten for the two modes
- Reviewed response-key list with a unit test (fixtures) and a live check (real API)
</objective>

<acceptance_criteria>

## AC-1: Business customers are returned in full except invoice links
```gherkin
Given INIO_REVEAL_PII is not true
When a tool returns an object with customerType "B" (get_customer, list_customers items, update_customer)
Then every field in that object and its nested objects is returned as the API gives it (emails, phones, address lines, zip, city, name, orgNr, vatNo, bank details, emails inside text)
And pdfURL / pdfUrl / digitalInvoiceURL are still "[redacted]"
```

## AC-2: Consumers and unknown types are redacted more strictly
```gherkin
Given INIO_REVEAL_PII is not true
When a tool returns an object with customerType "C", with any other value, or with no customerType and no known type
Then today's redaction applies (email/phone keys, emails in text, address lines, zipCode, ssn, iban, bankAccount, accountNumber, invoice links)
And customerName, city, yourReference and note are also "[redacted]" at any depth (case-insensitive)
And a nested object with its own customerType uses its own type, not its parent's
```

## AC-3: get_invoice uses the customer's type
```gherkin
Given INIO_REVEAL_PII is not true and an invoice whose customerId belongs to a "B" customer
When get_invoice is called (by id or number, with or without withInherited/includeWorkflowSettings)
Then the invoice is returned with business rules (only invoice links redacted)
And a second get_invoice for any invoice of the same customer does not fetch the customer again (cache shared by all requests of the server factory, at most 1000 entries)
And if the customer lookup fails or returns no valid customerType, consumer rules apply and the invoice is still returned (no error)
And with INIO_REVEAL_PII=true no customer lookup is made
```

## AC-4: Description, README and keys stay in sync
```gherkin
Given the new rules
When REDACTION_NOTE is read in any tool description
Then it states: business customers only have invoice links redacted; consumers and unknown types also have the listed fields redacted; INIO_REVEAL_PII=true disables it; invoices from write tools use consumer rules
And the README redacted-fields block lists both modes, and the existing guard test checks every consumer key and the business key set against src/redact.ts
And error messages keep today's strict handling (emails in text, per-field messages for sensitive keys) in both modes
```

## AC-5: Unreviewed response keys fail a check
```gherkin
Given a reviewed list of customer and invoice response keys, each marked consumer-redacted or shown
When the customer or invoice fixture contains a key not in the list (unit test), or the live API returns one (live suite, before release)
Then the test fails and names the unreviewed key
And the customer fixture uses customerType "B" (the spec enum), with a "C" variant covered in unit tests
```
