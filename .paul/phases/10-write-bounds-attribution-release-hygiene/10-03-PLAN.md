<objective>
## Goal
The small, cheap parts of AEGIS R6: every third-party action is pinned to a commit SHA, the release image is run before it is pushed, and GitHub rulesets stop force-pushes or deletion of `main` and moves or deletion of `v*` tags.

## Purpose
With a single maintainer and self-approved releases, the pipeline itself has to be hard to subvert: a moved action tag or a moved release tag should not be able to change what gets published.

## Output
- ci.yml and release.yml: `actions/checkout`, `actions/setup-node`, `actions/cache` pinned by SHA with a version comment (docker/* already are)
- release.yml image job: build amd64 locally, run an HTTP smoke test (401 without token, initialize 200 with token), then build and push multi-arch
- Two repository rulesets (created with `gh api` after your approval)
</objective>

<acceptance_criteria>

## AC-1: Actions pinned
```gherkin
Given ci.yml and release.yml
When every `uses:` line is listed
Then each references a 40-character commit SHA followed by `# vX.Y.Z`, and the SHA is the one GitHub reports for that tag (the release at least two weeks old)
```

## AC-2: Release image is run before it is pushed
```gherkin
Given the release image job, when the version is not yet published
When it runs
Then it first builds linux/amd64 with load: true, starts it with MCP_TRANSPORT=http, a 40-character test token and fake INIO_* values, and checks POST /mcp gives 401 without the token and 200 for initialize with it
And only then builds and pushes linux/amd64 and linux/arm64 (with the existing provenance and SBOM)
And a failing smoke test stops the job before anything is pushed
```

## AC-3: Rulesets protect main and release tags
```gherkin
Given the repository dnmitev/iniomcp
When rulesets are listed
Then "main" (target branch, default branch) blocks deletion and non-fast-forward pushes
And "release tags" (target tag, refs/tags/v*) blocks deletion and updates (tags can be created, not moved)
And merging PRs, pushing to main and pushing new tags keep working for the owner
```

## AC-4: Reviewed
```gherkin
Given the workflow diff
When devops-reviewer reviews it
Then it returns APPROVE (findings fixed)
```
