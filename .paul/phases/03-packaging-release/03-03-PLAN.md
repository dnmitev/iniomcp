<objective>
## Goal
No tool call waits forever. Every Inio API request and token request is aborted after a timeout. The default is 30 seconds and `INIO_REQUEST_TIMEOUT_MS` overrides it. A timeout becomes a clear tool error.

## Purpose
The v0.1.2-rc.1 live gate showed the test environment's invoice endpoints can stall for more than 30 seconds. Without a timeout the assistant hangs with no answer. The user asked for a generous default because the API can be slow.

## Output
Config option, timeouts in the API client and token provider, tests, a higher live-suite test timeout, a README row and a CHANGELOG line. Released as 0.1.2 together with the Node 26 image change.
</objective>

## AC-1: Configurable timeout
```gherkin
Given INIO_REQUEST_TIMEOUT_MS unset or empty
Then the request timeout is 30000 ms
Given an integer from 1000 to 600000
Then it is used
Given any other value (non-integer, below 1000, above 600000)
Then loadConfig fails with "INIO_REQUEST_TIMEOUT_MS must be an integer from 1000 to 600000"
```

## AC-2: API requests time out
```gherkin
Given the API does not answer within the timeout
When a tool calls the Inio API
Then the request is aborted and the tool returns "TIMEOUT: The Inio API did not respond within <n> s."
And a warn line is logged with method, path (no query string) and code TIMEOUT
And each attempt (including the 401 and 429 retries) has its own timeout
And the caller's other errors (network, 4xx/5xx) behave as before
```

## AC-3: Token requests time out
```gherkin
Given the token endpoint does not answer within the timeout
When a token is needed
Then the tool returns "The Inio auth server did not respond within <n> s (INIO_AUTH_URL)."
And no secret appears in the message or logs
```

## AC-4: Wiring, docs and live suite
```gherkin
Given createServer(config)
Then the API client and token provider both use config.requestTimeoutMs
And the README env table lists INIO_REQUEST_TIMEOUT_MS (default 60000)
And the live suite's per-test timeout is above the request timeout (e.g. 120 s), so a slow API shows up as a TIMEOUT tool result instead of a cut-off test
```

## Amendment (2026-10-29, review)
- Default lowered to 30 s (user decision). MCP clients commonly time out tool calls at 60 s (the MCP SDK's default), so a 60 s server timeout would lose the clear `TIMEOUT` result to a client-side timeout. Worst case per tool call (token refetch on 401, plus a 429 retry) is about 5 × timeout + 5 s.
- A timeout while reading the response body is reported as `TIMEOUT` too (API) or as the auth timeout message (token), not as UPSTREAM_ERROR or an invalid token response.
- The live suite passes a 120 s MCP client request timeout to every tool call, not just a longer test timeout.
- The README row documents the worst case and that seconds are rounded up.
