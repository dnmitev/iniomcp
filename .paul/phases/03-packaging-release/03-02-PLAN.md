<objective>
## Goal
Release 0.1.0. Pushing a `v*` tag runs one workflow that:
1. verifies the tagged commit
2. passes the live smoke suite against the test environment
3. publishes `@dnmitev/inio-mcp` to npm with provenance (OIDC trusted publishing, no token)
4. pushes a multi-arch image to `ghcr.io/dnmitev/inio-mcp`
5. creates a GitHub Release

A release candidate goes to npm `next` first and is checked on a clean machine before the final tag.

## Purpose
This completes the Phase 3 goal: 0.1.0 can be installed with `npx` and Docker. Every later release takes one tag.

## Output
release.yml, dependabot.yml, a digest-pinned Dockerfile base, the dated CHANGELOG, npm and GHCR artifacts for 0.1.0, and a GitHub Release.
</objective>

## Research (2026-10-29)
- **npm trusted publishing** ([docs.npmjs.com/trusted-publishers](https://docs.npmjs.com/trusted-publishers)):
  - Requires npm CLI ≥ 11.5.1 and Node ≥ 22.14. Locally: npm 11.11.0 with Node 24.14.1.
  - The workflow needs `id-token: write`. Provenance is generated automatically for a public package published from a public repository.
  - Workflow filename and environment are entered on npmjs.com exactly, case-sensitively, and are only checked at publish time.
  - `repository.url` must match the repository.
- **Existing package:** npm's docs do not say whether a trusted publisher can be configured for a package that does not exist yet. Community sources say it must exist first, so the first version has to be published manually:
  - [WordPress Playground release docs](https://developer.wordpress.org/playground/handbook/contributing/releases/)
  - [azu/setup-npm-trusted-publish](https://github.com/azu/setup-npm-trusted-publish)
  - One source mentions an org-level setting, which does not apply to a personal scope.
  - `@dnmitev/inio-mcp` is not on npm yet.
- **Pinned versions:**
  - Base image `node:24.14-alpine`, digest `sha256:8510330d3eb72c804231a834b1a8ebb55cb3796c3e4431297a24d246b8add4d5`
  - docker/login-action v3.7.0 `c94ce9fb468520275223c153574b00df6fe4bcc9`
  - docker/metadata-action v5.10.0 `c299e40c65443455700f0fdfc63efafe5b349051`
  - docker/setup-qemu-action v3.7.0 `c7c53464625b32c7a7e944ae62b3e17d2b600130`
  - docker/setup-buildx-action and docker/build-push-action keep the SHAs already in ci.yml.
- **Deferred items folded in:** Dependabot (actions, docker, npm) and the base image digest pin from 03-01; the CHANGELOG date at tag time.

## AC-1: Release workflow
```gherkin
Given a pushed tag vX.Y.Z or vX.Y.Z-rc.N on main's history
When release.yml runs
Then job verify (contents: read) checks out the tag and fails unless:
  - the tag equals "v" + package.json version
  - CHANGELOG.md has a "## [X.Y.Z…]" section with a date (final releases only)
  - lint, typecheck, unit, build, integration and package suites pass
And job live (environment "release") runs INIO_LIVE=1 npm run test:live with the four INIO_* secrets and fails the release on any failure
And job npm (environment "release", id-token: write) runs npm publish: final versions to "latest", -rc versions with --tag next; it skips if that version already exists on npm
And job image (packages: write) builds linux/amd64 and linux/arm64 from the Dockerfile and pushes ghcr.io/dnmitev/inio-mcp:X.Y.Z (plus X.Y and latest for final versions only), with provenance and SBOM attestations and OCI labels
And job release (contents: write) creates the GitHub Release for the tag with the CHANGELOG section as notes, marked pre-release for -rc
And npm, image and release run only after verify and live pass for the same commit
And third-party actions are pinned to commit SHAs, every job has a timeout, and the concurrency group never cancels a running release
And no secret is available to pull_request runs
```

## AC-2: Dependencies kept current


## AC-3: First release
```gherkin
Given the release environment and trusted publisher are set up
When v0.1.0-rc.1 is tagged
Then the workflow publishes @dnmitev/inio-mcp@0.1.0-rc.1 under "next" with provenance and pushes the rc image
And `npx -y @dnmitev/inio-mcp@next` in a clean node:24 container (dummy INIO_* values) answers tools/list with the seven tools
And `docker run -i ghcr.io/dnmitev/inio-mcp:0.1.0-rc.1` does the same on both amd64 and arm64 (arm64 via the registry manifest)
When v0.1.0 is tagged after that
Then @dnmitev/inio-mcp@0.1.0 is "latest" with provenance, ghcr.io/dnmitev/inio-mcp:0.1.0 / 0.1 / latest exist and are public, and the GitHub Release 0.1.0 exists
```

## Amendment (2026-10-29): 0.1.0 published manually
During the bootstrap, a second manual publish released `0.1.0` (built from main `efffde8`, same source, no provenance) in addition to `0.1.0-rc.0`. npm never reuses a version, so the first CI release moves up one patch version:
- AC-3 and Tasks 2-3 use `0.1.1-rc.1` and `0.1.1` instead of `0.1.0-rc.1` and `0.1.0`. GHCR tags become `0.1.1`, `0.1` and `latest`.
- `0.1.0` stays on npm as a valid release. `latest` moves to 0.1.0 now (it pointed at rc.0) and to 0.1.1 when CI publishes it.
- CHANGELOG: 0.1.0 is dated 2026-10-29 and marked as published manually without provenance; 0.1.1 is the first release built and published by CI with provenance, and the first Docker image.
