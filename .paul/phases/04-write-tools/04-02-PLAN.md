<objective>
## Goal
Add four write tools behind `INIO_ALLOW_WRITES`:
- `update_customer`: contact details and address only
- `reset_invoice_stage`
- `create_credit_invoice`: credit an existing invoice
- `match_credit_invoice`

## Purpose
Clients can fix customer contact data, correct an invoice's escalation stage, and credit invoices from the assistant. Each of these can affect the end customer (re-sending, credit notes) or money (fee waivers, credits). Defaults are therefore set so that nothing reaches the end customer unless the model asks for it explicitly.

## Output
Four tools, unit and integration tests, smoke-script coverage for `update_customer` (self-reverting), README and CHANGELOG.
</objective>

## Decisions (user, 2026-10-29)
- `reset_invoice_stage`: `redistribute` defaults to **false**, and the tool always sends it explicitly. `modifyInvoice` is not supported.
- Credit notes: `distributionEnabled` defaults to **false**. To send the note to the end customer, the model must set `distributionEnabled: true` and a `distributionMethod`.
- `update_customer`: contact and address fields only. These are customerName, the three distribution emails, mobilePhoneNo, customerAddress, shippingAddress and languageCode. Not allowed: SSN, orgNr, vatNo, customerType, workflowsSettings, metadata.

## API facts (04-API-NOTES)
- **PATCH /customers/{id|by-number}:** the schema is strict. null clears a field, and addresses merge partially. The three distribution emails must be distinct. Response is `[customer]`. Database only, no workflows.
- **POST /invoices/{id}/reset-stage:** by id only.
  - Fields: `targetStage` (invoiced|reminded); `dueDate` (required for invoiced, forbidden for reminded, must be after today); `reason` (1–100); `redistribute`.
  - Credit invoices and invoices in debt collection that are paid, closed or cancelled cannot be reset. A paid or closed reminded invoice needs its payment reversed first.
  - Starts the `resetInvoiceStage` workflow, which may **waive outstanding fees** and, with redistribute, **re-send to the end customer**. The response is the plan: targetStage, dueDate, plannedSteps, feeWaiveAmount, feePaidKept, willWaiveOutstandingFee, willRedistribute, willReRunSetup, workflowId.
- **POST /invoices/{id|by-number}/credit-invoice:**
  - Fields: `invoiceNo` (the credit note's own, unique number); `distributionMethod` (''|sms|email|paper|edi); `distributionEnabled`; `isReverseTaxation`; `invoiceItems` [{ debitItemId uuid, unitPrice ≤ 0, quantity }] (at least one).
  - Optional: description (≤100), paymentReference, paidDate (if in the past, `additionalInformation` is required), additionalInformation.
  - Credits must stay within the debit item's quantity, price and remaining amounts. Not allowed in debt collection. 409 on a duplicate invoiceNo.
  - Starts the `credit` workflow and returns 201 with the credit invoice and its items.
- **POST /invoices/{id|by-number}/match-credit-invoice:** `creditInvoiceNo`, `amount` ≤ 0, optional paidDate and additionalInformation. Both invoices must have the same customer, and |amount| must not exceed either remaining amount. Returns 200 with the credit invoice id. No distribution.
- Unmatched credit invoices (POST /invoices/credit-invoice) are left out: they need full item and calcInput data. They go to 04-03 or later.

## AC-1: update_customer
```gherkin
Given update_customer with exactly one of id (uuid) / number, and at least one of:
  customerName (2–100), distributionEmailAddress / distributionEmailAddress2 / distributionEmailAddress3 (email or null),
  mobilePhoneNo (^\+\d{1,17}$ or null), languageCode (EN|SV|BG|DE or null),
  customerAddress { countryCode (2 letters), city (1–50), zipCode (^[0-9A-Za-z ]{4,6}$), addressLine1 (1–60), addressLine2..5 (1–60 or null) } (partial),
  shippingAddress (same partial shape, or null)
When it is called
Then PATCH /customers/{id} or /customers/by-number/{number} is sent with only the given fields (null kept)
And duplicate distribution emails are rejected locally ("Distribution email addresses must be different.")
And the result is the updated customer (compact, redacted, without workflowsSettings)
And SSN, orgNr, vatNo, customerType, workflowsSettings, metadata and unknown keys are rejected by the input schema
```

## AC-2: reset_invoice_stage
```gherkin
Given reset_invoice_stage with exactly one of id / number, targetStage (invoiced|reminded), reason (1–100), redistribute (boolean, default false), dueDate (YYYY-MM-DD; required for invoiced, rejected for reminded)
When it is called with a number
Then the invoice id is looked up with GET /invoices/by-number/{number} first (the API resets by id only)
And POST /invoices/{id}/reset-stage is sent with { targetStage, dueDate?, reason, redistribute } (redistribute always present)
And the result is the API's plan (targetStage, dueDate, plannedSteps, feeWaiveAmount, feePaidKept, willWaiveOutstandingFee, willRedistribute, willReRunSetup), compacted, without workflowId
And the description warns that outstanding fees may be waived and that redistribute: true re-sends to the end customer
```

## AC-3: create_credit_invoice
```gherkin
Given create_credit_invoice with exactly one of id / number of the invoice to credit, creditInvoiceNo (1–50), items [{ debitItemId uuid, unitPrice ≤ 0, quantity > 0 }] (1–100 items),
  optional description (≤100), isReverseTaxation (default false), distributionEnabled (default false), distributionMethod (sms|email|paper|edi; required when distributionEnabled is true),
  paidDate (YYYY-MM-DD), additionalInformation (required when paidDate is before today)
When it is called
Then POST /invoices/{id or by-number}/credit-invoice is sent with { invoiceNo: creditInvoiceNo, invoiceItems, isReverseTaxation, distributionEnabled, distributionMethod: (method or ''), description?, paidDate?, additionalInformation? }
And the result is { created: true, id, invoiceNo, paymentReference, items (the API's creditInvoiceItems) }, compacted and redacted (amended 2026-10-29: the spec 201 has no totalAmount/currency/status)
And once the POST succeeds the tool never fails: an unreadable 2xx body gives { created: true, creditInvoiceNo, note }
And the description says that get_invoice lists the item ids (debitItemId), that unit prices are negative, that nothing is sent to the customer unless distributionEnabled is true, and that the credit is posted against the invoice
```

## AC-4: match_credit_invoice
```gherkin
Given match_credit_invoice with exactly one of id / number of the debit invoice, creditInvoiceNo (1–50), amount (number ≤ 0, at most 2 decimals), optional paidDate, additionalInformation (required when paidDate is in the past)
When it is called
Then POST /invoices/{id or by-number}/match-credit-invoice is sent with { creditInvoiceNo, amount, paidDate?, additionalInformation? }
And the result is { matched: true, invoice, creditInvoiceNo, amount, creditInvoiceId }, plus a read-back of the debit invoice's remainingAmount and paymentStatus (read-back failure → note, as in 04-01)
```
