<objective>
## Goal
Add write support to the client and register write tools only when `INIO_ALLOW_WRITES=true`. Ship five low-risk write tools:
- `create_customer_pause`
- `update_customer_pause`
- `cancel_customer_pause`
- `update_invoice_due_date`
- `update_invoice_stop_until_dates`

## Purpose
Clients who opt in can pause reminders and debt-collection transfers, and postpone due dates, from the assistant. These are the least risky writes: no money moves and nothing is sent to end customers. The plumbing (write gate, annotations, uncertain-outcome handling, audit actor) is the base for 04-02 and 04-03.

## Output
Client `post`/`patch`, the write gate, five tools, unit and integration tests, an opt-in live write suite, README and CHANGELOG. Released as 0.2.0 at the end of the phase, or per plan if the user wants.
</objective>

## Decisions (user, 2026-10-29)
- **Scope order:** low-risk first. 04-01 covers pauses and invoice dates. 04-02 covers customer update, reset stage and credit invoices. 04-03 covers creating customers and invoices, payments and reversal.
- **Safety:** tool annotations plus an echo of what changed. No extra confirm parameter. Writes are registered only with `INIO_ALLOW_WRITES=true`.
- **Live tests:** an opt-in `INIO_LIVE_WRITES=1` suite against a test customer and invoice named in `.env`. It never runs in the release gate.

## Facts from the API (see notes)
- No dry-run endpoints and no role checks for public clients. The tenant comes from the token.
- Pauses: `startAt` must be tomorrow or later; overlapping pauses return 409; cancelling is irreversible; an active pause can change only `endAt`.
- Due date: postpone only, so the change cannot be reverted with this endpoint. It triggers the client webhook `invoiceDueDatePostponed`.
- Stop-until dates need the `MANUAL_STOP_UNTIL_FLAG` feature flag, otherwise the endpoint is blocked. A date can be cleared with null.
- Audit actor: `x-user-real-name` header or `userRealName` in the body.

## AC-1: Write plumbing
```gherkin
Given client.post(path, body, options?) and client.patch(path, body, options?)
Then they send JSON (content-type application/json) with the same auth, 401 retry, 429 retry, timeout, envelope unwrapping and error mapping as get()
And a timeout on POST/PATCH returns TIMEOUT with the message "The Inio API did not respond within <n> s. The change may or may not have been applied; check before retrying."
And the query string and the body are never logged
And every write request sends header x-user-real-name: "inio-mcp" so audit records show the change came from the MCP server
```

## AC-2: Write gate and annotations
```gherkin
Given INIO_ALLOW_WRITES unset or false
Then no write tool is registered (tools/list shows the 7 read tools only)
Given INIO_ALLOW_WRITES=true
Then the 5 write tools are also listed
And every write tool has readOnlyHint false, destructiveHint true, openWorldHint true and idempotentHint false
And cancel_customer_pause and update_invoice_due_date say in their description that the change cannot be undone with these tools
```

## AC-3: Customer pause tools
```gherkin
create_customer_pause { customerId (uuid), scope (reminders|dcTransfers|both), startAt (YYYY-MM-DD), endAt? (YYYY-MM-DD), reason (1–255) }
  → POST /customers/{customerId}/pauses with { scope, startAt, endAt, reason } and returns the created pause (compacted, redacted, without temporalWorkflowId)
update_customer_pause { customerId, pauseId, startAt?, endAt? (date or null for indefinite), scope?, reason } (at least one of startAt/endAt/scope)
  → PATCH /customers/{customerId}/pauses/{pauseId}; returns the updated pause
cancel_customer_pause { customerId, pauseId, reason }
  → POST /customers/{customerId}/pauses/{pauseId}/cancel; returns the cancelled pause
And input dates are strict YYYY-MM-DD; endAt must be after startAt when both are given (checked locally)
And API validation errors are returned with their field errors: "<CODE>: <message> (correlationId …) Fields: <field>: <message>; …"
```

## AC-4: Invoice date tools
```gherkin
update_invoice_due_date { id | number, dueDate (YYYY-MM-DD), reason (1–100) }
  → POST /invoices/{id}/update-due-date or /invoices/by-number/{number}/update-due-date with { dueDate, updateReason: reason }
  → returns { invoice: <id or number>, dueDate, updated: true } and, read back via GET, the invoice's new dueDate and stage (compact)
update_invoice_stop_until_dates { id | number, reason, invoicing1..4?, collection1..5? (date or null) } (at least one stop date)
  → POST .../update-stop-until-dates with { metadata: {<step>StopUntilDate: …}, escalationStopReason: reason }
  → returns the invoice's stop-until dates read back via GET
And a blocked endpoint (feature flag off) or a business-rule rejection is returned as the API's error text
```

## AC-5: Integration, live and docs
```gherkin
Given the fake Inio API with routes for the five endpoints
Then integration tests cover each tool with INIO_ALLOW_WRITES=true, and that the tools are absent without it
Given INIO_LIVE_WRITES=1 with INIO_LIVE_WRITE_CUSTOMER_ID (and optional INIO_LIVE_WRITE_INVOICE_NUMBER)
Then a live suite creates a pause starting in 30+ days, updates its endAt, cancels it, and checks it is cancelled
And sets and then clears a stop-until date on the invoice when the invoice is given (skips with a note if the API reports the feature flag is off)
And never calls update_invoice_due_date (irreversible) unless INIO_LIVE_WRITE_DUE_DATE=1 is also set
And the README documents INIO_ALLOW_WRITES, the five tools, what each one changes, and the irreversible ones
```
