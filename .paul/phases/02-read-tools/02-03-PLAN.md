<objective>
## Goal
Finish Phase 2:
- Handle HTTP 429 with one bounded retry.
- Make `workflowsSettings` opt-in on `get_invoice` and `get_customer`.
- Cover all seven read tools in the integration suite.
- Confirm in Claude Desktop that a client can explore customers, invoices, pauses and retry attempts conversationally.

## Purpose
Rate limits must not surface as confusing errors. Detail calls should cost about half the tokens they do now, while stage-specific settings (distribution method, fees, escalation per invoicing1–4) stay one flag away. The integration suite must guard every tool against the built server, not just get_invoice.

## Output
429 handling in the client, an `includeWorkflowSettings` flag on two tools, fake-API routes and synthetic fixtures for every read endpoint, integration tests, a README tool list, and a verified Desktop session.
</objective>

## Facts
- Live sizes: get_invoice ~2,050 tokens, get_customer ~1,130. `workflowsSettings` (distributionMethods, distributionEnabled, escalationTiming/Fees/ServiceFees/Enabled, templates, other) is the largest block in both.
- `workflowsSettings` matters for questions about how and when an invoice stage (setup, invoicing1–4, paid, credit) is distributed or escalated, so it stays available behind a flag (user decision, 2026-10-28).
- 429 policy (decided 2026-10-28): one retry honoring Retry-After, capped at 5 s, then RATE_LIMITED.
</context>

<acceptance_criteria>

## AC-1: 429 handling
```gherkin
Given the API answers 429 with Retry-After: 2
When client.get is called
Then it waits 2 s (via an injectable sleep), retries once with the same URL and headers, and returns the result if the retry succeeds
And Retry-After as an HTTP date is honored, missing or invalid Retry-After waits 1 s, and any wait is capped at 5 s
When the retry also returns 429
Then it throws InioApiError(429, 'RATE_LIMITED', 'The Inio API rate limit was reached. Try again in <n> s.') with n = the second Retry-After (rounded up, minimum 1)
And a warn line is logged with method, path, status 429 and the wait, never the query string
And the 401 retry still works and is independent (a 401 then 429 then 200 succeeds)
```

## AC-2: Opt-in workflowsSettings
```gherkin
Given get_invoice or get_customer without includeWorkflowSettings (default false)
Then the result has no workflowsSettings key at any depth of the invoice / customer object
Given includeWorkflowSettings: true
Then workflowsSettings is included (compacted, redacted as before)
And the input description tells the model when to use it: distribution method (email, SMS, paper), escalation fees and timing, or enabled stages for setup, invoicing1–4, paid or credit
And withInherited on get_invoice keeps working with and without the flag
```

## AC-3: Integration coverage
```gherkin
Given the fake API serves synthetic fixtures for customers (list, by id, by number), customer pauses (list, by id), invoices (list, by id, by number, with-inherited) and retry attempts, in the real envelope shapes
When the built server is spawned against Keycloak and the fake API
Then each of the seven tools returns the expected compact, redacted JSON
And list_invoices with status ['open'] sends status=open&status=open
And an invoice number that the fake API answers with 429 then 200 succeeds, and one answered with 429 twice returns "RATE_LIMITED: …"
And fixtures contain synthetic values only
```

## AC-4: Claude Desktop
```gherkin
Given the built server configured in Claude Desktop with the test environment
When the user asks for open invoices of a customer, a customer and their pauses, an invoice's retry attempts, and how an invoice's reminders are distributed
Then Claude picks the right tools, uses includeWorkflowSettings only for the distribution question, and PII is redacted
```
