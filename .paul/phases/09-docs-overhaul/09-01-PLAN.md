<objective>
## Goal
A user of Claude Desktop, Claude Code, VS Code or Cursor finds one guide for their client that covers local (npx), Docker and the team's hosted server, plus examples of what to ask. README becomes an overview that links to them. Stale docs are fixed (AEGIS R10).

## Purpose
The MCP is meant to replace a hand-written integration; that only works if setup is obvious per client and people know what to ask. Drift (wrong package name, tool count, missing upstream references) erodes trust in the docs.

## Output
- `docs/setup/{claude-desktop,claude-code,vscode,cursor}.md`
- `docs/hosting.md` (shared HTTP server, moved from README; Phase 11 adds Helm here)
- `docs/examples.md`
- README slimmed: overview, quick start, links, tools, write tools, data protection, release model, development
- PLANNING.md marked historical; AS-7100 references in workaround comments
- `test/unit/docs.test.ts`: every pinned version equals package.json; every relative docs link resolves
</objective>

<acceptance_criteria>

## AC-1: One setup guide per client
```gherkin
Given a user of Claude Desktop, Claude Code, VS Code or Cursor
When they open docs/setup/<client>.md
Then it shows, with copy-pasteable config pinned to the current version: local via npx (four INIO_* variables), Docker, and the team's hosted HTTP server with a bearer token
And it says where the config file lives, how to keep the secret out of plaintext where the client allows (VS Code input prompt, Claude Code read -rs), how to check the server is connected, and where logs are
And Claude Desktop's hosted option uses mcp-remote pinned to a version at least two weeks old (0.15.1) with an Authorization header, verified to connect to a locally started HTTP server
And every command and config key was checked against the client's current docs or CLI help (claude mcp add --help)
```

## AC-2: Hosting guide
```gherkin
Given an admin who wants one server for the team
When they open docs/hosting.md
Then it contains the Shared HTTP server and Security content from today's README (token, Docker, reverse proxy, one tenant per server, 256 KiB cap, non-loopback warning)
And a short "which setup should I use" comparison (local vs hosted)
```

## AC-3: Usage examples
```gherkin
Given a new user
When they open docs/examples.md
Then they find example prompts grouped by task (find a customer, invoice status, overdue and payment questions, pauses, retry attempts, and opt-in writes such as postponing a due date or recording a payment)
And each write example says the tool asks for confirmation and what it changes
And a short note explains why some fields show "[redacted]" (customer type), linking to Data protection
```

## AC-4: README is an overview that links out
```gherkin
Given the README on GitHub and on npmjs.com
When a reader opens it
Then it has: what it is, a quick start (Claude Desktop, npx), a table of setup guides, configuration variables, tools, write tools, logs, data protection, release model, development
And links into docs/ are absolute GitHub URLs (https://github.com/dnmitev/iniomcp/blob/main/docs/...) so they work on npmjs.com, where docs/ is not shipped
And the redacted-fields blocks and their guard test are unchanged and passing
```

## AC-5: Drift fixed and guarded
```gherkin
Given the docs and comments after this plan

```
