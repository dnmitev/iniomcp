<objective>
## Goal
With `MCP_OAUTH_ISSUER` and `MCP_PUBLIC_URL` set, the HTTP server acts as an OAuth 2.1 protected resource: it publishes Protected Resource Metadata (RFC 9728), answers unauthenticated `/mcp` requests with `401` plus `WWW-Authenticate: Bearer resource_metadata="…"`, and accepts JWT access tokens issued by that provider for this resource. The static `MCP_AUTH_TOKEN` keeps working. Tool-call and write log lines carry the signed-in user.

## Purpose
Claude on the web, Desktop connectors and mobile only offer OAuth sign-in on personal plans, so business users without npx or Docker can reach the hosted server only this way. Ease of use: nothing changes for deployments that do not set the new variables.

## Output
- `src/oauth.ts`: token verifier (JWKS via OIDC discovery, issuer, audience, expiry, signature) and the PRM document
- `src/config.ts`: `MCP_OAUTH_ISSUER`, `MCP_PUBLIC_URL`, optional `MCP_OAUTH_AUDIENCE`; `MCP_AUTH_TOKEN` optional when OAuth is on
- `src/http.ts`: PRM routes, async bearer gate (static token first, then JWT), challenge header, `authInfo` passed to the MCP handler
- User (`sub`, `preferred_username`) in tool-call/write logs
- Unit tests (local keys) and an integration test against the Keycloak test container
</objective>

## Research (2026-11-03)
- Claude connectors (claude.com/docs/connectors/building/authentication):
  - The hosted apps' redirect URI is `https://claude.ai/api/mcp/auth_callback`.
  - PKCE S256 is always used.
  - A `401` with `resource_metadata` is required to start sign-in.
  - PRM `resource` must equal the server URL exactly, path included.
  - Only the first `authorization_servers` entry is used.
  - The authorization server must serve RFC 8414 or OIDC discovery itself.
  - Scopes come from the challenge `scope` or the PRM `scopes_supported`; `offline_access` is appended when the authorization server lists it.
  - Refresh happens on 401 and up to 5 min before expiry; rotate refresh tokens for public clients.
  - Egress is from `160.79.104.0/21`.
  - Custom connectors can use a client ID the user enters (public client, secret optional), CIMD or DCR.
- The `@modelcontextprotocol/server` 2.4.0 SDK exports:
  - `requireBearerAuth` / `verifyBearerToken` (verifier interface, `expectedResource` compared with `AuthInfo.resource`, rejects a missing `expiresAt`);
  - `bearerAuthChallengeResponse`;
  - `buildOAuthProtectedResourceMetadata` / `getOAuthProtectedResourceMetadataUrl`;
  - `oauthMetadataResponse`, which also wants an RFC 8414 document;
  - `AuthInfo` (`clientId`, `scopes`, `expiresAt`, `resource`, `extra`).

  `handler.fetch(request, { authInfo })` surfaces it to tools as `ctx.http.authInfo`.
- Keycloak issues `aud` through an audience mapper rather than from the RFC 8707 `resource` parameter, so the server checks `aud` contains the audience (default: `MCP_PUBLIC_URL`).
- `jose` 6.x is already in the tree (through the dev-only MCP client). It becomes a direct dependency, because Node has no JWT/JWKS verification.

## AC-1: Configuration
```gherkin
Given MCP_TRANSPORT=http
When MCP_OAUTH_ISSUER is unset
Then behaviour is exactly as today (MCP_AUTH_TOKEN required, no PRM routes, 401 without resource_metadata)
When MCP_OAUTH_ISSUER is set
Then MCP_PUBLIC_URL is required (absolute https URL ending in /mcp; http only for localhost) and the issuer must be https (http only for localhost)
And MCP_OAUTH_AUDIENCE defaults to MCP_PUBLIC_URL
And MCP_AUTH_TOKEN becomes optional, but when set its existing rules still apply
And invalid values fail startup with one clear line each, like the other config errors
And the startup log line states whether OAuth is on and the issuer (never tokens)
```

## AC-2: Protected Resource Metadata
```gherkin
Given OAuth is on
When a client sends GET or HEAD to /.well-known/oauth-protected-resource or /.well-known/oauth-protected-resource/mcp
Then it gets 200 application/json without a token: { resource: MCP_PUBLIC_URL, authorization_servers: [issuer], bearer_methods_supported: ["header"], resource_name: "Inio MCP" }, with Access-Control-Allow-Origin: *
And the reply is sent before any body is read, is not logged as unauthorized, and makes no network call
And other methods on those paths, other /.well-known paths, and the same paths with OAuth off get 404 as today
```

## AC-3: Challenge
```gherkin
Given OAuth is on
When /mcp is called without a token, with a malformed header, or with a token that is neither the static token nor a valid access token
Then the reply is 401 with WWW-Authenticate: Bearer resource_metadata="<origin of MCP_PUBLIC_URL>/.well-known/oauth-protected-resource/mcp" (plus error="invalid_token" when a token was sent)
And it is still sent before the body is read, with Connection: close, and counted by the existing 401 throttle
```

## AC-4: Access tokens accepted
```gherkin
Given OAuth is on
When /mcp gets Authorization: Bearer <JWT> signed by a key from the issuer's JWKS (found through <issuer>/.well-known/openid-configuration), with iss = issuer, aud containing the audience, exp in the future
Then the request is served as with the static token
And tokens with another issuer, without the audience, expired, not yet valid (nbf), with a bad signature, signed with "none" or HS* algorithms, or unparseable get 401 (AC-3)
And JWKS keys are cached and refetched on an unknown kid (jose remote JWKS), and the discovery document is fetched once and cached; a provider outage gives 401 for new tokens without crashing the server and logs one warn (throttled like the 401 warn)
And the static token is checked first (constant-time, as today), so header clients keep working while the provider is down
```

## AC-5: User in logs
```gherkin
Given a request authenticated with an access token
When a tool runs
Then its tool-call log line (and the write log line for writes) includes user: { sub, name } where name is preferred_username when present
And requests with the static token log no user field
And no token, claim set or other personal data beyond those two fields is logged
```

## AC-6: Integration with a real provider
```gherkin
Given the Keycloak test container with a realm client that issues user access tokens (direct access grant enabled for the test client only) and an audience mapper for the test MCP URL
When the integration test gets a user token and calls tools/list over HTTP
Then it gets 200, while a token from the existing client-credentials client (no matching audience) gets 401, and PRM is served
```
