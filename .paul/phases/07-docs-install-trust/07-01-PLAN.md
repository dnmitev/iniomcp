<objective>
## Goal
1. **R1, privacy claim:** replace "Personal data is redacted" in 17 tool descriptions and the README with one exact statement of what is redacted and what is not. Add a README "Data protection" section.
2. **R7, install trust:** pin the package version and image tag in every README example, keep secrets out of copy-paste examples, pin the inspector in `package.json`, and add a "Release model" note.
3. **README drift from Phase 6:** the 256 KiB body cap, 401 before the body is read, the non-loopback warning, and the write-outcome wording.

## Purpose
AEGIS F-05-001 (high), F-05-002, F-05-003 and F-05-006: the claim "personal data is redacted" overstates the denylist. Names, city, address1, orgNr, references and free text reach the LLM provider. F-04-008: unpinned `npx -y` and the floating `:0.3` tag in copy-paste configs amplify a compromised publish across tenants. This must be accurate before the stakeholder presentation, and R2 (narrower redaction) will later change only the key list, not the wording structure.

## Output
- `src/redact.ts`: an exported `REDACTION_NOTE` constant (one sentence), used by every tool description in place of the old sentence.
- README: Tools section wording, a new "Data protection" section, a "Release model" note, pinned examples, an updated HTTP Security list, and write-outcome wording.
- `package.json`: `inspect` script pins `@modelcontextprotocol/inspector@<current version>`.
- Tests that fail if the README's redacted-key list or the descriptions drift from `isSensitiveKey`.
</objective>

<acceptance_criteria>

## AC-1: One accurate redaction sentence in every tool description
```gherkin
Given the 17 tools whose descriptions said "Personal data is redacted unless …"
When the tool list is read
Then each description contains the same sentence, exported from src/redact.ts. It names what is redacted: email addresses (also inside text), phone numbers, address lines, zip code, SSN, IBAN and bank account numbers, and PDF/digital invoice links. It says that names, city, organisation and VAT numbers, references, free text and amounts are not redacted, and that INIO_REVEAL_PII=true turns redaction off.
And no description still contains "Personal data is redacted"
```

## AC-2: README states the same and adds Data protection
```gherkin
Given README.md
When a reader looks at the Tools section and the INIO_REVEAL_PII row
Then the wording matches AC-1, with no claim that "personal data is redacted" without qualification
And a "Data protection" section states:
  - tool results, including non-redacted personal data, go to the LLM provider of the user's assistant, so the tenant needs a processor agreement with that provider
  - the server stores nothing; it only logs (stderr)
  - create_customer and update_customer arguments (SSN, contact details) reach the provider in the user's prompt and the tool call whatever INIO_REVEAL_PII says
  - logs contain customer and invoice numbers, tool names and outcomes, but no tokens or secrets
And a unit test fails if the README's list of redacted fields and isSensitiveKey disagree (drift guard for R2)
```

## AC-3: Install examples are pinned and keep secrets out of copy-paste
```gherkin
Given every README install and config example (npx, Claude Desktop, Cursor, VS Code, Docker, shared HTTP server)
When a reader copies it
Then npx runs `@dnmitev/inio-mcp@0.4.0`, not an unpinned name, and Docker uses `ghcr.io/dnmitev/inio-mcp:0.4.0`, not `:0.3`
And the README says how to pin by digest (`docker buildx imagetools inspect …`) and how to verify npm provenance (`npm audit signatures`)
And the Claude Desktop/Cursor JSON examples keep a placeholder secret but warn that the file stores it in plaintext and how to restrict it (VS Code keeps its input prompt)
And package.json's inspect script pins the inspector to the installed version
```

## AC-4: Release model note
```gherkin
Given README.md
Then a short "Release model" note says: single maintainer; releases are built by GitHub Actions with npm provenance and published to npm and GHCR from tags; how to verify (npm audit signatures, image digest); the package moves to the @inio scope later
```

## AC-5: README matches Phase 6 behaviour
```gherkin
Given the README HTTP Security list and the write tools section
Then it says requests over 256 KiB get 413 (not 4 MB), and that the token is checked before the request body is read
And that binding to a non-loopback host (the Docker image's 0.0.0.0) logs a warning
And the write-outcome sentence covers timeouts, network errors and server errors, plus "accepted but unreadable" success notes
```

## AC-6: Nothing else changes
```gherkin
Given lint, typecheck, unit, integration and package tests
When they run
Then all pass. The only src change is the description sentence; behaviour is unchanged.
```
